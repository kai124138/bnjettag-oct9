## Claude · 14:39

Dug into all of it. Short version up front: **the Job is not what's making things feel slow, and the kernel you connected is the right mechanism.** Here's the full picture.

## 1. The reframe — a Job is not "batch"

You're reading `kind: Job` as "submit and wait." It isn't. The Job is only *how the pod gets scheduled*. Once the pod is `Running`, there's a live JupyterLab server sitting inside it, and every cell you execute runs **immediately** — there's no queue, no submission, nothing batch about it. Today's log entry: the smoke train (3 epochs, 20,000 jets) took **84 s wall, 61.4 s of it actual training** on the 2080 Ti the pod landed on.

The two delays you actually feel:

| delay | how long | why |
|---|---|---|
| `./lab.sh up` → usable | **~2.5 min** (warm) | container start + `import tensorflow` over CephFS |
| first-ever start | **41 min** | cold venv build on the PVC, one time, already paid |
| connecting | seconds | but only if `./lab.sh forward` is running — it wasn't |

That's it. After that it's as responsive as a local notebook.

## 2. The 6-hour limit — there are two separate clocks, and only one is ours

**Ours:** `activeDeadlineSeconds: 21600` in [kai-lab.yaml](nrp-lab/kai-lab.yaml#L13). We wrote that. We could raise or delete it.

**Nautilus's:** their [cluster policy](https://nrp.ai/documentation/userdocs/start/policies/) says interactive pods *"will be destroyed in 6 hours unless you request an exception for your namespace"*, and caps interactive pods at 2 GPUs / 32 GB RAM / 16 CPU cores. So 6 h is the platform norm, not a choice we invented.

I could **not** confirm whether their 6 h reaper actually targets *Job*-managed pods (ours is a Job, which is a controller — the reaper is aimed at uncontrolled pods). It's never been tested because our own deadline fires first.

But the policy that really bites is the utilization one, on the same page: **GPU utilization must exceed 40% of what you requested**, CPU 20–200%, RAM 20–150%. A notebook holding a GPU at 0% while you think about what to type is precisely what that rule exists to stop. No deadline exception lifts it.

**And hitting 6 h costs you almost nothing.** The venv, the notebooks and everything in `/data/lab/outputs` live on the `kai-data` PVC, not in the pod. One `./lab.sh up` and 2.5 minutes and you're back exactly where you were. That was a deliberate design choice, not an accident.

## 3. What actually happened when you connected the kernel

The chain, end to end:

1. **Job → pod on a GPU node.** The container's last line is `jupyter lab --ip=0.0.0.0 --port=8888` ([kai-lab.yaml](nrp-lab/kai-lab.yaml#L110-L113)).
2. **That server is unreachable from your laptop.** It binds port 8888 on the pod's private cluster IP (`10.244.218.13` right now). No Ingress, no NodePort, no public address — by design.
3. **`kubectl port-forward` tunnels through the Kubernetes API server.** `localhost:8888` on your Mac → apiserver → kubelet on the node → pod:8888. Authenticated with your OIDC token, encrypted with the same TLS as every other kubectl call. No firewall hole, no exposed service. This is why the tunnel must stay open — kill it and the connection dies.
4. **The token authenticates you** to the Jupyter server, which is why `lab.sh url` has to ask the pod for it.
5. **VS Code speaks the standard Jupyter protocol** over that tunnel — REST to list/start kernels, a websocket to ship cells and stream outputs back. "Existing Jupyter Server" is just VS Code being a Jupyter client.
6. **The kernel is an `ipykernel` process spawned inside the pod** as a child of the Jupyter server, so it inherits everything the container exported: `PYTHONPATH=/data/lab/repo/bnjettag/code/hgq2`, `BNHGQ2_TRAIN_DATA`, `BNHGQ2_OUT_ROOT`, `KERAS_BACKEND`, and the `LD_LIBRARY_PATH` fix for TF 2.21's broken RPATH. That's the whole reason `import bnhgq2` works and TF sees the GPU with zero setup in the notebook.

Your laptop does nothing but render text. All compute, all data, all GPU is in San Diego.

## 4. Is "kernel" the right option?

Yes — a Jupyter kernel *is* the "responds right away" model. There's no lighter mechanism.

The one real alternative to Jupyter, if you'd rather have a full IDE than notebook cells: run **`code-server`** (VS Code in a browser) inside the pod instead of JupyterLab, reached through the identical `kubectl port-forward`. Same tunnel, same env, but you get a terminal and a file tree in the pod rather than a notebook. Worth doing if you find yourself mostly editing files and running scripts rather than poking at arrays. I have not tried whether the VS Code Kubernetes extension can attach directly to a pod — don't take my word either way on that.

## 5. Is there something we can ask NRP admins for?

Two things exist, and neither is as good as what you already have:

**(a) A namespace exception to the 6 h limit.** Real — the policy names it and points at [Nautilus Support](https://nrp.ai/contact). Two catches: it's granted *per namespace*, and `cms-ml` is the whole Duarte group's, so the request would go through Russell or Javier, not you. And the framing in the docs is for namespaces running *"JupyterHub or some other application controlling the pods for you"* — i.e. they'd rather you run something that manages its own lifecycle than hand you an unbounded GPU pod. It also wouldn't exempt you from the 40%-GPU-utilization rule.

**(b) The hosted JupyterHub at https://jupyterhub-west.nrp-nautilus.io.** Log in with CILogon, pick hardware from a spawner, done — genuinely zero setup. **But it can't work for this project**, for a hard structural reason: a PVC is namespace-scoped in Kubernetes, so a hub session running outside `cms-ml` cannot mount `kai-data`. No `/data/hls4ml_lhc_jet`, no `/data/lab/venv`, no `/data/lab/repo`. And the home directory is *"limited to 5GB"* — the dataset tarballs alone are ~2.7 GB train + ~1.14 GB val, before a TensorFlow venv. It's fine for scratch Python. It is not a replacement for `kai-lab`.

## 6. Colab, or the home PC?

The thing that discriminates here is **not GPU power**. The model is 18,657 parameters and the pod runs it on a 2080 Ti. Compute is irrelevant. What matters is *environment parity* — CLAUDE.md's rule that an interactive environment which has drifted from the batch environment "is worse than none, because it lies."

**Colab: no.** It fights that rule directly. Colab ships its own TensorFlow/numpy, and we need `tensorflow==2.21.0`, `keras==3.15.0`, `hgq2==0.1.9`, `numpy==2.5.0` exactly — you'd be reinstalling the whole pinned stack every session, and re-staging 2.7 GB of data, and you'd still have no `kai-data`. It's the worst fit of the three.

**Home PC: yes, and the repo already planned for it.** [docs/infrastructure/home-pc-cluster-recreation.md](docs/infrastructure/home-pc-cluster-recreation.md) is a complete build plan for exactly this, with verification gates. Its own verdict:

> **Replaces well**: the full dev loop — training small/tiny/r8 models (minutes per run on the 4060 Ti), conversions and C-sim, whole-model csynth at deployable scale (hours, one at a time), ROC evaluation, everything offline.
> **Doesn't replace**: parallel seed sweeps (one GPU vs the cluster's dozens), the 6.4M-parameter monolith synthesis (>100 GB RAM), concurrent syntheses.

Two honest caveats. The doc specs a **4060 Ti 8 GB** (you said 4060 — for a 19k-param model it makes no difference either way). And I have **no evidence the plan was ever executed** — the deliverable `HOME-PC.md` would live on that machine, not here. Phases 0–3 are the training setup and are the only ones you'd need for notebooks; Phase 4 (Vitis, ~110 GB install) is a separate, heavy question you can skip.

If you can reach that box over SSH, VS Code Remote-SSH would give you a notebook that feels entirely local, with the dataset on local NVMe instead of CephFS — genuinely faster than the pod for the fiddling loop. How to make it reachable from campus is something I haven't looked into.
