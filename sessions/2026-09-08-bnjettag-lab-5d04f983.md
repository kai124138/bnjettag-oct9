## How the kernel actually gets set up

There is no kernel registration anywhere in this repo. It's four things falling into place:

1. **The kernelspec comes free with the venv.** `ipykernel` (7.3.0, pulled in transitively by the `jupyterlab` install) ships `share/jupyter/kernels/python3/kernel.json` in its wheel, so installing it into `/data/lab/venv` puts a spec there. Confirmed live — `jupyter kernelspec list` shows exactly one: `python3 → /data/lab/venv/share/jupyter/kernels/python3`.

2. **Launching Jupyter by venv abspath is what makes it visible.** `kai-lab.yaml:112` does `exec "$VENV/bin/jupyter" lab`, so `sys.prefix` is the venv and `$VENV/share/jupyter` is on the kernelspec search path. Nothing else is.

3. **Env inheritance.** `kai-lab.yaml:100-108` exports `KERAS_BACKEND`, `LD_LIBRARY_PATH` (the nvidia-`*`-cu12 wheel libs — the TF 2.21 RPATH workaround), `BNHGQ2_TRAIN_DATA/OUT_ROOT/STORE`, `PYTHONPATH` and `WANDB_MODE` **before** the exec. Kernels are children of the server process, so they inherit all of it. That's why cell 1 of the notebook can just print `os.environ` and why `import bnhgq2` needs no path juggling.

4. **The notebook binds without a prompt** because `build_notebooks.py:16` stamps `kernelspec.name = "python3"`, which matches. (Display name differs — "Python 3" vs the venv's "Python 3 (ipykernel)" — irrelevant, matching is on `name`.)

One nice detail that looks accidental but isn't: `lab.sh sync` pushes to `/data/lab/repo/bnjettag/code/hgq2`, so `config.py`'s four-levels-up `PROJECT_ROOT` resolves to `/data/lab/repo` — "the directory that contains `bnjettag/`", exactly as the docstring intends. The batch job's `--strip-components=1` into `/work/code` resolves `PROJECT_ROOT` to `/`, which is why `store.py:14` carries that override comment. The pod's layout is more faithful than the cluster's.

**Pins:** all nine match `kai-bn14-l1x3-n8-w1a8-s1.yaml` verbatim — tensorflow 2.21.0, keras 3.15.0, quantizers 1.2.2, sklearn 1.9.0, h5py 3.14.0, wandb 0.28.0, hls4ml 1.3.0, numpy 2.5.0 (hgq2 0.1.9 still installing). Same `python:3.12` base image.

## The three gaps worth closing

**1. The kernel resolves correctly by rescue, not by design.** `kernel.json`'s `argv[0]` is bare `"python"`, and PATH in the pod is untouched — `which python` is `/usr/local/bin/python`, the image's system interpreter with no TensorFlow in it. What saves it is `jupyter_client/manager.py:391-402`, which rewrites `argv[0]` to `sys.executable` precisely for the "launched by abspath without activating the env" case. It works, but the same missing PATH means **`!pip install x` in a notebook cell installs into `/usr/local`, not the venv** — a silent trap. One line fixes both: `export PATH="$VENV/bin:$PATH"`.

**2. The venv-reuse branch never re-checks the pins.** `if [ ! -x "$VENV/bin/python" ]` is the wrong sentinel twice over: a pod killed mid-install passes it, and if you bump the pins for round 15 the pod prints `[venv] reusing existing $VENV` and silently keeps the old environment — the exact drift CLAUDE.md calls worse than no interactive environment. The only guard is the `import tensorflow, keras, hgq2` line, which prints two versions and compares them to nothing. Fix: write the pin string to `$VENV/.pins` after a successful install, compare on start, rebuild or fail on mismatch.

**3. No staleness gate on the synced code.** The batch YAML has three explicit fail-fast gates (config file present, `feature_indices` in `data.py`, `wandb_util` in `train.py`). The pod has none, and `/data/lab/repo` persists on the PVC across sessions — forget `lab.sh sync` after editing and the kernel imports last week's code with no signal. Cell 3 prints the `bnhgq2` path but nothing about its age. Fix: have `sync` drop a `.synced` stamp (date + `git rev-parse --short HEAD` of the research tree) and print it in cell 3.

Two smaller ones: notebook cell 4 uses `os.environ["PYTHONPATH"]` as if it were a single directory (`os.path.join(PYTHONPATH, "configs", ...)`) — true today, false the moment anything appends to it, as the batch job does; and the README's "~10 min" first build is at 36 min and counting (downloads were running at ~600 kB/s on this node), so "expect 30-40 min" is the honest number.

Also: the notebook's checks are eyeball-only. `assert sys.prefix == "/data/lab/venv"` in cell 1 and `assert inspect.getfile(bnhgq2).startswith("/data/lab/repo/")` in cell 3 would turn the two things I flagged above into cells that fail loudly.
