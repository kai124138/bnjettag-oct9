# TreeLUT: An Efficient Alternative to Deep Neural Networks for Inference Acceleration Using Gradient Boosted Decision Trees

- **Authors:** Alireza Khataei, Kia Bazargan — University of Minnesota.
- **Venue / Year:** FPGA 2025 (ACM/SIGDA Int'l Symp. on Field Programmable Gate Arrays), Feb 27–Mar 1, 2025, Monterey, CA, pp. 14–24, doi: 10.1145/3706628.3708877.
- **arXiv:** 2501.01511 — https://arxiv.org/abs/2501.01511, HTML https://arxiv.org/html/2501.01511
- **Code:** https://github.com/kiabuzz/treelut
- **Topic area:** LUT-native inference for FPGAs — **not a neural network**, included only as the "non-NN rival at the same latency class" per task scope.

## TL;DR
Not a neural network at all — a hardware compiler for **Gradient Boosted Decision Trees (GBDTs)**, mapped to a three-stage pipeline (key generator → decision-tree comparisons implemented as multiplexer cascades → adder tree) using only LUTs, no BRAM, no DSP. Included here purely as a same-latency-class, same-benchmark-suite (JSC + network intrusion + MNIST) data point for how far a *non-neural* classical-ML method reaches on identical hardware/task, since it recurs as a comparison baseline in every recent LUT-native-NN paper (NeuraLUT-Assemble Table IV, the family survey).

## (a) Mechanism
Trains a standard GBDT model (outside the FPGA toolflow, e.g. via a standard boosting library), quantizes split thresholds and leaf values, then synthesizes the tree ensemble as a pipelined cascade of comparisons/multiplexers/adders directly in LUT logic — architecturally unrelated to the truth-table-enumeration trick used by LogicNets/PolyLUT/NeuraLUT (there is no "neuron," no backprop-trained fan-in-restricted network at all).

## (b) What it explicitly does NOT do
- Not a neural network method of any kind — irrelevant to "does it consume a pretrained network" in the LUT-NN sense; it consumes a pretrained **GBDT**, which is a fundamentally different model class from anything BNJetTag produces.
- No attention/matmul/sequence support (not applicable — decision trees don't have those concepts).
- Its own stated limitation, quoted directly from the family survey (arXiv:2506.07367) citing TreeLUT's own text: **"may struggle with highly unstructured inputs such as images or sequential data, where DNNs excel."**

## (c) Exact published jet-tagging numbers — Table 5, primary source (arXiv HTML, cross-validated against NeuraLUT-Assemble's independent Table IV citation of the same numbers — exact match)
JSC dataset (per TreeLUT's own Table 4/§4.2): **16 input features, 5 classes** — the same OpenML-sourced JSC task. Target: Zynq UltraScale+ MPSoC / **xcvu9p-flgb2104-2-i** family device.

| Config | Accuracy | LUT | FF | Latency | F_max |
|---|---|---|---|---|---|
| **TreeLUT (I)** | 75.6% | 2,234 | 347 | 2.7 ns | 735 MHz |
| **TreeLUT (II)** | 74.6% | 796 | 74 | 1.1 ns | 887 MHz |

(A separately-quoted headline elsewhere in the paper — "best design using only 170 LUTs and 233 FFs at 724 MHz" — refers to a **different task's** (network intrusion detection) smallest operating point, not JSC; do not conflate the two when citing "TreeLUT's smallest design.")

Claimed general improvement over prior LUT-native NN work: **~4–101× lower area-delay product** at competitive accuracy (own abstract), and ~97% on MNIST.

## Verdict
**ORTHOGONAL** — a genuinely different model class (trees, not neural networks), included only as a latency-class comparison point. Its presence in this space is informative for one thing only: it shows the JSC task's ceiling is being approached from *multiple* algorithm families (GBDTs, LUT-native MLPs, and conventional hls4ml DNNs) simultaneously, reinforcing that the 16-feature/5-class JSC problem itself is thoroughly picked-over territory — **not** evidence about transformer/attention compilation, which no tree-based method addresses.
