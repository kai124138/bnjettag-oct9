# Replication targets — arXiv:2510.24784 + companion code (HGQ2-examples/jsc150)

**Companion to** `2510.24784_submicrosecond_transformers_jet_tagging_fpga.md` (the science dossier).
This file exists for one purpose: to state, with maximum precision, **what we can and cannot
replicate**, and what number counts as a hit.

- **Paper:** Laatu, **Sun**, Cox, Gandrakota, Maier, Ngadiuba, Que, Luk, Spiropulu, Tapper,
  *Sub-microsecond Transformers for Jet Tagging on FPGAs*, **arXiv:2510.24784v1** (26 Oct 2025),
  NeurIPS 2025 ML4PS workshop, FERMILAB-PUB-25-0779-CMS-LDRD. 7 pages incl. refs.
  https://arxiv.org/abs/2510.24784 — local PDF in this directory, read in full 2026-08-04.
- **Code read:** `reference-code/HGQ2-examples`, `github.com/calad0i/HGQ2-examples`,
  HEAD `6cdc6e3` "feat: lut transformer", **2026-07-02** — i.e. the code is **eight months
  downstream of the paper**. Directory `jsc150/` (`model.py`, `run_train.py`, `run_test.py`,
  `data.py`, `tools/prepare_data.sh`) plus top-level `gather_statistics.py`.
- Note: **Chang Sun is 2nd author, not 1st.** He is 1st author on the sibling MLP-Mixer paper
  (arXiv:2503.03103) and on da4ml (arXiv:2507.04535), both of which this paper leans on.

## Lead finding — most of what we want to replicate against is not in the paper

The task asked for accuracy-vs-EBOPs Pareto points, LUT/FF/DSP/BRAM/CARRY8, latency in ns *and*
cycles, clock period targeted *and* achieved, and the training recipe. **The paper publishes
roughly a third of that.** Verbatim inventory:

| Quantity | In the paper? |
|---|---|
| Accuracy (%) per variant per N | **Yes** — Table 1 |
| Per-class OvR AUC | **Yes** — Fig. 2 legends (numeric, 5 classes × 4 N × 2 models) |
| Latency (ns) | **Yes** — Table 1 |
| LUT (k) | **Yes** — Table 1 |
| II (clock cycles) | **Yes** — Table 1, `1` for every HGQ-trained row |
| DSP | **Yes** — Table 1, `0` for every HGQ-trained row |
| **EBOPs per model** | **No.** Only a *shared training target* of **350,000** (§3). Fig. 1 is accuracy vs N, **not an accuracy–EBOPs Pareto front.** There is no Pareto plot in this paper. |
| **FF / CLB registers** | **No** |
| **BRAM / URAM** | **No** |
| **CARRY8** | **No** |
| **Latency in cycles** | **No** (only ns; with II=1 and no clock stated, cycles are not recoverable) |
| **Clock period targeted** | **No** |
| **Clock period achieved / WNS** | **No** |
| **Synthesis stage (csynth vs post-route)** | **No** — §3 says only "Vitis HLS and Vivado" |
| Epochs, batch size, LR, optimizer | **No** |
| β schedule | **Only** "a PID controller over β" (§3). No gains, no setpoint dynamics. |
| Train/val split | **No** (train 620k / test 260k stated; val split not stated) |
| d_model, n_layers, FFN dim, param count | **No** |
| Softmax treatment | **Never mentioned** |
| Device | **Yes** — Xilinx **XCU250** (§3) |

**So: the replication target is Table 1 + Fig. 2, and nothing else. Everything else has to be
taken from the code, and the code disagrees with the paper in several load-bearing places
(below). Any "we reproduced X" claim must name whether X came from the paper or the repo.**

**reproducing their failure**, not their result.

16→32→64. Fig. 1 caption concedes this: the 64-particle accuracy drop "is expected due to the
fixed resource budget we enforced during training."

## Target C — device, latency, clock

- **Device: Xilinx XCU250** (§3), the Alveo U250 Virtex UltraScale+ die — same 1,728,000-LUT,
  4-SLR silicon class as our VU13P target.
- "350,000 EBOPs — roughly one Super Logic Region of the target XCU 250 chip" (§3). That is the
  only statement tying EBOPs to a device budget.
- **Latency is given in ns only.** With II = 1 and no clock stated, the cycle count is not
  recoverable from the paper. Their sibling paper [18] closes at **200 MHz / 5 ns on an XCVU9P
  with Vitis HLS 2023.2 + Vivado 2023.2**; if that convention holds here, 104 ns ≈ 21 cycles —
  **but this is inference, not a paper fact, and must be labeled as such.**
- **Post-route vs csynth: the code settles this.** `gather_statistics.py` reads
  `output_<top>/reports/<top>_post_route_util.rpt` and `<top>_post_route_timing.rpt`. Their
  reported numbers are **post-place-and-route**, not HLS estimates. Our 3.91M/4.80M LUT figures
  are csynth estimates. **These two stages are not comparable**; our own single-layer anchor had
  csynth over-estimating LUT by 2.29–2.51× (`results/adder-graph/e1/POSTSYN.md`).

## The code: recipe, and where it disagrees with the paper

### Data (`jsc150/data.py`, `tools/prepare_data.sh`)

- Source: **Zenodo record 3602260**, `hls4ml_LHCjet_150p_train.tar.gz` and
  `hls4ml_LHCjet_150p_val.tar.gz`, converted to `150c-train.h5` / `150c-test.h5`. The Zenodo
  **`val` split is used as the test set** — that is the 260,000 jets.
- `X[:, :n_constituents]` — the 150-particle file is *sliced*, so `jsc150` covers N=8…150 from one
  file. The paper only ever uses N ∈ {8, 16, 32, 64}. **N=150 is untested in the paper.**
- `-f 3` selects **feature columns `[5, 8, 11]`** and then applies a **pT gate**:
  `X *= X[..., :1] >= 2` (zeroes every constituent whose column-5 value is < 2). This gate is not
  mentioned in the paper.
- Standardization: global mean/shift and std/scale over axes (0,1) computed on **train+val
  combined**, applied to test. Stored as float16.
- **Validation split: `val_size=0.1`** after a `np.random.shuffle` — so **558,000 train /
  62,000 val / 260,000 test.** The paper states only 620k/260k.

### Training (`jsc150/run_train.py`) — none of this is in the paper

- Backend **JAX** (`KERAS_BACKEND=jax`), `jax_default_matmul_precision='tensorfloat32'`.
- Seeds: `np.random.seed(42)`, `random.seed(42)`. **No Keras/JAX seed** — runs are not bit-exact.
- Optimizer **Adam** (default params), loss `SparseCategoricalCrossentropy(from_logits=True)`,
  `steps_per_execution=4`.
- **Batch size 2790**, **initial LR 3e-3**, **epochs = 7000**.
- LR: custom `cosine_decay_restarts_schedule(3e-3, first_decay_steps=500, t_mul=1.0, m_mul=1.0,
  alpha=1e-6, alpha_steps=10)`. Driven by Keras `LearningRateScheduler`, so the step argument is
  the **epoch index** — i.e. a cosine restart **every 500 epochs**, 14 cycles over the run, with
  no decay of the peak (`m_mul=1.0`).
- **β schedule — the biggest delta.** Code uses an **open-loop** `BetaScheduler` with
  `PieceWiseSchedule([(0, 2e-8, 'linear'), (2000, 3e-7, 'log'), (7000, 3.0e-6, 'constant')])`:
  β ramps linearly 2e-8 → 3e-7 over epochs 0–2000, then log-spaced 3e-7 → 3e-6 over 2000–7000,
  then constant. **The paper says "a PID controller over β … to enforce the target EBOPs" (§3).
  There is no PID controller in the released code.** Replicating the code will *not* land on a
  fixed 350k EBOPs; it will land wherever the open-loop ramp puts it.
- Model selection: **`ParetoFront` over `(val_accuracy ↑, ebops ↓)`**, checkpointing only when
  `val_accuracy > 0.5 and ebops < 5e5`. Filenames encode
  `epoch=…-val_acc=…-train_acc=…-ebops=…-val_loss=…`. So the repo's selection rule is a
  **two-objective front**, and the 350k figure in the paper is a *post-hoc pick off that front*,
  not a hard constraint. Early stop: `StopIf(ebops < 1e4)`.
- Quantizer init (`get_model(..., bw_k=7, bw_a=7, l1_reg=1e-8, ...)`):
  - weights: `default_q_type='kbi'`, `b0=7`, `i0=0`, `overflow_mode='wrap'`,
    `fr=ir=MonoL1(1e-8)`, `i_decay_speed=1e-3`
  - datalane: `default_q_type='kif'`, `f0=7`, `overflow_mode='wrap'`, `fr=MonoL1(1e-8)`,
    integer bits constrained `ic=MinMax(0, 12)`
  - `LayerConfigScope(beta0=0)` — β starts at 0 and is driven entirely by the scheduler.

### Synthesis (`jsc150/run_test.py`, `gather_statistics.py`)

- Default path is **alkaid/da4ml native RTL emission**, not hls4ml. `--hls4ml` / `--hls4ml-da`
  are opt-in flags. The paper describes the hls4ml path; the current repo has moved on
  (commit `93f1455` "chore(jet150): migrate to alkaid").
- `HWConfig(1, -1, -1)`, `solver_options={'hard_dc': 2}`, `latency_cutoff=2` (pipelining depth
  knob), **`clock_period` default `1.0` ns**, **`clock_uncertainty=0.0`**. A 1 ns default target
  is not the paper's regime and is almost certainly not what Table 1 was built at.
- `trace_and_save` runs `trace_minmax` over train+val to fix integer bits before conversion
  (`--no-growth` forbids bitwidth increase). This calibration pass is **not described in the
  paper at all** and materially affects the final bitwidths.
- `gather_statistics.py` extracts, per project, from **post-route** reports: `DSPs`,
  `LUT as Logic`, `LUT as Memory`, `CLB Registers`, **`CARRY8`**, `Register as Latch`,
  `Register as Flip Flop`, `RAMB18`, `URAM`, `RAMB36/FIFO*`, plus WNS from the timing summary.
  Derived: `LUT = logic + memory`, `FF = FF + latch`, **`actual_period = clock_period - WNS`**.
  Latency is recovered as **`count of 'reg' in the top-level .v minus 1`** — i.e. pipeline stages,
  a *cycle* count.
  **Conclusion: FF, BRAM, URAM, CARRY8, target clock and achieved clock all exist in their
  tooling and were simply not printed in the 4-page workshop paper.** If we run their flow we
  get numbers the paper does not have; those are *ours*, not theirs, and must be labeled so.

### Model variants — paper names vs code names

| Paper name | Code `--model` | Definition in `jsc150/model.py` |
|---|---|---|
| Multi-Head Attention | `xfm` | `get_transformer`: d_model 24 → `QAffinedUnaryFunctionLUT('tanh')` → `QMultiHeadAttention(h=2, key_dim=16)` → residual → tanh → FFN 32 → 24 → residual → `QGlobalAveragePooling1D` → 32/32/32 → 5. **h = 2**, one encoder block. |
| Linformer (proj dim 2) | `xfmt` | `get_llformer`: `QDenseT(16)` → `QLinformerAttentionT(h=1, k=4, d=16)` → residual → 2× `QDenseT(16)` → residual → GAP → `QDenseT(16)` → `QDenseT(5)`. **k = 4, h = 1**, all-`QDenseT` (LUT/table) datapath. |
| Deep Sets (HGQ) | `gnn` | `get_gnn`: 64-wide, `QSum` pooling with `scale=2^-round(log2 N)` then `1/16`, head 64/32/16/5. |
| MLP Mixer [18] | `mlp_mixer` | `get_mlpm`: token-mixing `bnc,nN->bNc` + channel MLPs, width 16. |
| — (not in paper) | `mlp`, `salt`, `gnn_t`, `gnn_pk`, `gnn_pkq`, and every `*_uq1` | `QSALTAttention(h=2, 16, 8, conv_size=5)`; table-based GNN; per-kernel GNN. |

**Three code/paper deltas on the transformers specifically:**

1. Paper §2.1: *"vanilla multi-head attention … with a single attention head."* Code `xfm` uses
   **`h=2`**. Either the code drifted or the paper's "single head" is wrong.
2. Paper Fig. 1 legend: *"Linformer proj dim 2."* Code `xfmt` uses **`QLinformerAttentionT(h, 4, d)`
   → k = 4**. Drifted.
3. Code `xfmt` is the **`QDenseT` / table-based ("LUT transformer") variant added in HEAD commit
   `6cdc6e3`, 2026-07-02 — eight months after the paper.** It is *not* the architecture Table 1
   was synthesized from. Replicating `xfmt` as-is will not reproduce row 5–8.

**`uq1` = the permutation-invariance switch.** Paper §2.2: *"Value-wise heterogeneous quantization
is also applied in the datapath, which breaks the otherwise permutation-invariant model to further
reduce the firmware footprint."* In code this is `homogeneous_axis=(0,)` (per-particle bitwidths,
permutation-breaking — **the paper's setting, and the default**) vs `homogeneous_axis=(0,1)` for
`*_uq1` (uniform across the particle axis, permutation-preserving). **The `_uq1` variants are the
ablation the paper never published**, and they are the only variants whose per-token instances are
identical — i.e. the only ones that could be folded.

## What we can steal

1. **Run `gather_statistics.py` unmodified against our own Vivado projects.** It is 130 lines and
   already parses post-route util + timing into the exact schema we lack: LUT split
   logic/memory, FF, CARRY8, RAMB18/36, URAM, WNS → `actual_period`, and cycle latency from `reg`
   count in the top `.v`. Adopting their extractor makes our numbers stage-comparable to theirs
   in one step. This is the single highest-value import in the repo.
2. **Their model-selection rule: a two-objective Pareto front over (val_accuracy, cost), not a
   best-val checkpoint.** `ParetoFront` with `enable_if=lambda x: val_acc>0.5 and ebops<5e5`.
   We currently select on val AUC alone. Substituting our per-token-slice LUT census for EBOPs
   (EBOPs is the wrong currency for ±1 weights — it excludes the accumulator, which *is* the
   entire cost of a binary design) gives us a cost-aware selection rule we do not have.
3. **The β ramp as an actual schedule.** `PieceWiseSchedule([(0,2e-8,'linear'), (2000,3e-7,'log'),
   (7000,3e-6,'constant')])` over 7000 epochs — a two-decade, two-phase ramp, far longer and
   gentler than anything in our R13 β arms. Worth one arm.
4. **`trace_minmax` calibration before conversion**, with a `--no-growth` variant. An explicit
   post-training integer-bit calibration pass on train+val.
5. **Baselines we should quote (never merge with ours):** Linformer-8 macro-OvR **0.8970** and
   MHA-8 **0.8970**, at 230k/246k LUT post-route, 0 DSP, II=1 — always with "3 features, N=8".
6. **The `_uq1` ablation.** Running `xfmt` vs `xfmt_uq1` measures exactly the cost of preserving
   permutation invariance — which is the cost of keeping instances foldable. Nobody has published
   this. It is a clean, cheap, thesis-relevant experiment sitting in their repo.

## What threatens us

1. **DSP = 0 is theirs already, and it is not binary-specific.** Every HGQ row in Table 1 —
   including Deep Sets and MLP-Mixer, which have no attention — reports **0 DSP at every N**,
   post-route, including the attention core. Our flagship spends 1,764 DSP at II=8 (14,112 at
   II=1). **On the DSP axis our story is currently weaker than theirs, not stronger.** The thesis
   must be pitched on the *mechanism* (uniform ±1 → one adder-tree topology, foldable identical
   instances) rather than on the DSP=0 outcome.
2. **"First transformer for jet tagging on FPGA" is taken** (abstract, Oct 2025). Our claim has to
   be "first *binary-weight* transformer" or the compiler mechanism.
3. **Binary looks like a strictly worse special case of learned mixed precision.** Fig. 3 shows
   HGQ discovering 1-bit weights where they pay and 0-bit (pruned) elsewhere, at better accuracy
   than our binary flagship on the same data. Our structural answer — per-value widths make
   instances non-identical, so *nothing in their design can be folded*, which is why every row is
   II=1 — is supported by their own numbers, but it is the only answer we have.
4. **Their smaller model matches our binary AUC at ~1/20 the LUT.** 0.8970 (3 feat, N=8, 230k LUT
   post-route, II=1) vs our 0.8902 (16 feat, N=10, 4.80M LUT **csynth**). The stage mismatch may
   account for a factor 2.3–2.5 of that; it does not account for 20×.
5. **We cannot fully replicate them, and should say so rather than quietly diverging.** The
   released code has no PID controller, uses h=2 not h=1, k=4 not k=2, defaults to 16 features not
   3, defaults to a 1 ns clock, and its `xfmt` is a post-paper LUT-transformer. **A "replication"
   of 2510.24784 from this repo is a replication of the repo, not of Table 1.** Any run we
   publish must carry the commit SHA `6cdc6e3` and an explicit delta list.

## How we'd cite it

> Sub-microsecond transformer jet taggers have been demonstrated post-place-and-route on a Virtex
> UltraScale+ XCU250 with heterogeneously quantized attention trained to a fixed ~350k-EBOPs
> budget, reaching 78–140 ns at II = 1 with zero DSPs and 202–279k LUTs
> [Laatu et al., arXiv:2510.24784]; that design buys device fit entirely on the precision axis at
> full spatial parallelism, which a uniform {−1,+1} weight constraint forecloses.

**Verdict: essential** (as a replication target and a rival), **with a hard caveat**: the paper is
a 4-page workshop note whose reproducible content is Table 1 and Fig. 2, and the companion code
has drifted materially past it. Treat repo results and paper results as two different sources.
