# From PyTorch to Calyx: An Open-Source Compiler Toolchain for ML Accelerators

- **Authors:** Jiahan Xie, Evan Williams, Adrian Sampson
- **Venue / Year:** 7th Compilers for Machine Learning workshop (C4ML 2026); arXiv posted
  2025-12-09
- **arXiv:** 2512.06177 — https://arxiv.org/abs/2512.06177
- **PDF:** https://arxiv.org/pdf/2512.06177 / HTML: https://arxiv.org/html/2512.06177v1
- **Topic area:** compiler / IR / hardware backends (Calyx/CIRCT candidate evidence)

## TL;DR
An end-to-end open-source toolchain — PyTorch → Allo (accelerator design language) → Calyx
(hardware IR) → CIRCT (LLVM's hardware-compiler infra) → synthesizable SystemVerilog — with
demonstrated FFNN, CNN, **and a small multi-head-attention (2 heads, 21-dim subspace of a
42-dim embedding, causal masking)** benchmark. Directly relevant as the most concrete existing
evidence for "does a Calyx/CIRCT NN frontend exist, and does it reach attention." Self-
describes as a research/prototyping platform, explicitly **not yet competitive with Vitis HLS
on resources** at the time of writing.

## Key methods / contributions
- Compiler passes for **memory partitioning** (banking multi-dimensional buffers to unlock
  parallel access) — the paper's main technical contribution; addresses a genuine Calyx
  weakness (naive per-bank control-flow explosion, `c^d` branches for `d`-dim/`c`-way
  partitioning) via a bank-index-as-extra-dimension trick.
- No fixed-point/quantization/low-bitwidth story: "a full, general **floating-point** library
  for Calyx" (Berkeley HardFloat) — no mention of constant/binary weights, quantization, or
  low-bitwidth arithmetic found in what we extracted.
- Explicitly scoped out: **"We leave hardware pipelining, resource sharing, and compilation of
  the backward pass for future work."**

## Main results
"Figure 2 shows Vitis outperforming Calyx across all baseline models"; "Calyx consumes
significantly more LUTs and FFs [than Vitis, which uses more BRAM]"; memory-partitioning
factor 2→4 gives a **3.05× speedup** on the FFNN benchmark; abstract claims "performance gain
up to 2.21×" (context/baseline for this figure not fully extracted — treat as a partial
optimization win, not a resource-competitiveness claim). Authors state plainly: **"Vitis
incorporates many mature and often implicit optimizations that are not currently implemented
in our Calyx-based flow."**

## Relevance to BNJetTag
The best concrete, dated (Dec 2025) evidence for our Q4 IR-candidate evaluation of
Calyx/CIRCT: (1) it confirms a working PyTorch→Calyx→CIRCT→SystemVerilog path exists and has
been pushed as far as a toy multi-head-attention block — i.e. attention is not structurally
impossible in this stack; (2) it confirms, in the authors' own words, that this path is
**currently behind Vitis HLS on resource efficiency** and missing pipelining/resource-sharing
— exactly the maturity gap our design doc's "realistic integration cost for one undergrad-year"
criterion needs to weigh; (3) it is itself evidence of the *scale* of project a
single-author/small-team, ~1-year effort can produce in this space (a comparable calibration
point for our own token-axis-folding ambition), while carrying no evidence yet either way on
constant-weight/binary specialization, which is our thesis's central lever.
