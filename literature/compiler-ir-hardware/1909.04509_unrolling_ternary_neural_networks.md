# Unrolling Ternary Neural Networks

- **Authors:** Stephen Tridgell, Martin Kumm, Martin Hardieck, David Boland, Duncan Moss,
  Peter Zipf, Philip H.W. Leong
- **Venue / Year:** ACM Transactions on Reconfigurable Technology and Systems (TRETS), Vol.
  12, Issue 4 (2019); submitted arXiv 2019-09-09.
- **arXiv:** 1909.04509 — https://arxiv.org/abs/1909.04509
- **PDF:** https://arxiv.org/pdf/1909.04509
- **Topic area:** compiler / IR / hardware backends (MCM/CSE applied to a quantized NN)

## TL;DR
The clearest "direct occupant" we found for MCM/adder-graph-style optimization applied to a
**ternary**-weight (`{-1,0,1}`) neural network on FPGA — and notably, three of the seven
authors (Kumm, Hardieck, Zipf) are core figures in the classical multiple-constant-
multiplication (MCM) / common-subexpression-elimination literature (Kumm's RPAG/ILP work,
Hardieck's SAT/ILP-based MCM), i.e. the MCM community's own people applied their toolkit to a
ternary NN.

## Key methods / contributions
- Ternary weights known at compile time → each row of a matrix-vector multiply becomes an
  **unrolled, pruned adder tree** ("the weights are stored in the routing"): a `0` weight
  prunes that input entirely, `±1` weights become a plain add/subtract input to the tree — no
  multiplier, no shift-and-add decomposition needed (ternary, like binary, is the
  single-signed-digit degenerate case of MCM).
- Reports removing **90% of the operations** in convolutional layers by combining weight
  sparsity (many zeros) with this compile-time unrolling.
- Target: Amazon AWS F1 instance (Xilinx UltraScale+ VU9P-class FPGA), VGG-style CIFAR-10
  network.

## Main results
**90.9 ± 0.1% CIFAR-10 accuracy, 122k frames/s, latency 29 µs.** Exact LUT/DSP/FF/BRAM
numbers were not extractable from the abstract-level sources fetched this session — flag for
a follow-up direct PDF read if exact resource counts are needed for a citation.

## Relevance to BNJetTag
Structurally the closest published precedent to our own binary-dense synthesis: like our
`{-1,+1}` weights, ternary weights need no multiplier, and the "adder tree with weights
stored in the routing" description is exactly what Vitis HLS's own inlined-constant Latency
path already does for us (per Sun's HGQ2 tutorial, already logged in
`research-log.md` 2026-07-04 §6 — ≤2-signed-digit weights get no multiplier). This paper
predates and did not need da4ml/adder-graph CSE machinery to get a good result — the "trivial
degenerate MCM case" story is consistent across both papers. It does **not** address
attention/einsum layers (2019, pre-dates hls4ml/FINN attention support entirely) and does not
report whole-network DSP/LUT numbers we could verify — cite the latency/accuracy/throughput
figures only, and treat resource claims as unverified pending a direct PDF read.
