# CGRA4ML: A Framework to Implement Modern Neural Networks for Scientific Edge Computing

- **Authors:** G. Abarajithan, Zhenghua Ma, Zepeng Li, Shrideep Koparkar, Ravidu Munasinghe,
  Francesco Restuccia, Ryan Kastner (UC San Diego; University of Moratuwa, Sri Lanka)
- **Venue / Year:** arXiv preprint August 2024 (v2); journal version in ACM Transactions on
  Reconfigurable Technology and Systems (DOI 10.1145/3801097, publication year not confirmed
  this session).
- **arXiv:** 2408.15561 — https://arxiv.org/abs/2408.15561
- **PDF / HTML:** https://arxiv.org/html/2408.15561v2
- **Topic area:** compiler / IR / hardware backends (hls4ml-adjacent, fastml ecosystem)

## TL;DR
A hardware/software/firmware co-design framework that generates a parameterizable
Coarse-Grained Reconfigurable Array (CGRA) in SystemVerilog RTL (not HLS C++), explicitly
positioned to handle **larger** models than hls4ml/FINN can by allowing off-chip weight
storage and a reused, reconfigurable PE array — i.e. a throughput-oriented, area-amortized
design, not a fully-spatial fixed-latency one.

## Key methods / contributions
- PE array with data reuse (weight/activation stationary per tile), off-chip DMA for weights
  too large to fit on-chip — the opposite tradeoff from hls4ml `io_parallel`'s "everything
  resident, everything unrolled" model.
- Transformers are supported by **decomposing them into existing bundle primitives**
  ("we provide classes that are internally built using multiple bundles and decomposed... to
  enable models such as transformers with ease") — **no native attention/einsum operator**;
  no discussion found of attention's act×act structure specifically.
- Binary/ternary weights are mentioned only as a QKeras-inherited *quantization* capability
  ("fixed point, binary, and ternary quantization techniques are available in QKeras") with
  **no CGRA4ML-specific binary-weight results or hardware specialization** (e.g. no
  DSP-elimination claim tied to binary weights) found in the parts of the paper we extracted.

## Main results
Reports throughput/efficiency metrics (e.g. "37.3 GOPs/W" for ResNet-50 at 250 MHz) rather
than fixed latency; cycle count for a layer scales as a product of tiling factors
(`OT·IT·(1+N·HT·W·(1+IS·KH))`) — i.e. latency is a function of how many tiles/iterations a
given (larger-than-fabric) layer needs, not a single fully-spatial pass.

## Relevance to BNJetTag
**Verdict: wrong latency class for our thesis.** CGRA4ML solves a different problem — fitting
*larger* models that don't fit hls4ml's spatial model, at the cost of a throughput-pipeline
(tiled, DMA-fed) architecture rather than hls4ml `io_parallel`'s single fully-unrolled,
fixed-II pass. Our trigger-latency requirement (~25 ns/token, sub-µs whole-model, II≈10) wants
the opposite of CGRA4ML's design point (reuse hardware across tiles/iterations, tolerate
off-chip access latency). It also does not offer a native attention/einsum operator (relies on
decomposition into existing primitives) or any binary-weight-specific hardware path — so it
neither solves our EinsumDense-inlining wall nor our token-folding ambition; it is not a
compiler/IR candidate for this design doc's problem, only a note for "what if the model grows
too large for spatial synthesis" (a different, adjacent question).
