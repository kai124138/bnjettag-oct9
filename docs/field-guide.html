How do I kill a job, and find jobs that are idle or stuck?2026-10-02

1 · Let the doctor find them

python3 nrp-lab/nrp_doctor.py status

It lists your kai- jobs and pods and flags three problems:

HUNG/IDLE POD: Running for over 2 h with no log line in the last 2 h. An idle GPU breaks Nautilus policy.
FAILED JOB: failed in the last 72 h with no active pods. Its W&B run may still say "running".
Pending: with the scheduler's reason.

2 · Check a suspect by hand

kubectl get pods -n cms-ml | grep kai-                # AGE vs STATUS
kubectl logs <pod> -n cms-ml --tail=20 --timestamps  # when did it last say anything?
kubectl exec <pod> -n cms-ml -- nvidia-smi          # GPU-Util near 0% = idle

3 · Save the evidence before killing it

kubectl logs <pod> -n cms-ml > ~/lab/bnjettag/local/<pod>.log
kubectl exec <pod> -n cms-ml -- cat /proc/1/wchan; echo   # what the process is blocked on

Write one entry in .claude/memory/cluster-inventory.md ending with a Check line.

4 · Kill the right thing

kubectl delete pod <pod> -n cms-ml     # hung pod: the Job starts a fresh one (uses a retry)
kubectl delete job <job> -n cms-ml     # stop the run for good: takes all its pods
./launch_r14.sh delete                 # a whole round (from variants/)

Delete the pod to retry a hung run, and the Job to stop it for good. Deleting only a pod of a job you want gone just makes the Job start another.

5 · Close the books

For a killed or failed run, mark its W&B run as crashed or finished in the W&B UI, so it doesn't sit "running". Lab notebook pod: nrp-lab/lab.sh down. Only touch names starting with kai-.

Tutorial

Learning to drive it yourself

In order. Each step builds on the last; by step 7 you can run a round without help.

  1. Know the three places things live

    This laptop holds code, configs, manifests, results and notes, and does light work only. Nautilus runs training in throwaway pods. W&B is where checkpoints and curves survive after the pods die. mulder is a fourth, used only for FPGA synthesis.

    Most confusion comes from asking "which copy is this?". The answer is almost always: the code on the laptop is the truth, the ConfigMap is a snapshot of it, the checkpoint lives in W&B, and the numbers come from .npz files on the laptop.

  2. Read four files once

    SYSTEM.md (how research runs), CLAUDE.md and RULES.md (what Claude does and doesn't do), docs/infrastructure/manual-round-runbook.md (a full round, step by step). After that, docs/cheatsheet.md is all you need at the terminal.

  3. Learn five kubectl verbs

    get (what exists), logs (what it said), apply -f (create from a file), delete (remove), exec -it (shell inside). Always add -n cms-ml. Everything else is a variation.

    kubectl get jobs,pods -n cms-ml | grep kai-
kubectl logs -f <pod> -n cms-ml
kubectl apply -f <file>.yaml -n cms-ml
kubectl delete job <job> -n cms-ml
kubectl exec -it <pod> -n cms-ml -- /bin/bash

    A Job is the order ("train this config"). A pod is the worker that carries it out. If a pod dies, the Job makes a new one, up to its retry limit.

  4. Understand the ConfigMap, because it bites

    The pod doesn't see your laptop. It sees a frozen tarball of the code that you uploaded. If you change code and forget to rebuild the ConfigMap, the cluster runs the old code without complaint. That's why the build script prints an md5 and every pod prints it back.

  5. Do one round by hand, one job first

    Follow "Launch training" in the tree above. Don't skip the single job. Read its whole log once so you know what healthy looks like; after that, a broken log stands out.

  6. Check once, then leave

    After the five milestone lines show up, the run takes care of itself. Check back hours later with get jobs and logs --tail=50. Watching it adds nothing, and having an agent watch it is the most expensive way to do it.

  7. Tell a monitor from a result

    The AUC in the training log and W&B is validation AUC, used to pick the best epoch. The number that goes into anything is ROC-test AUC on the held-out split (n = 260,000), recomputed from the .npz, averaged over at least 3 seeds, with an interval. Two arms whose intervals overlap are tied. Compare only at the same N and the same input set (for example l1x3).

  8. Run the hardware branch

    Accuracy alone doesn't answer the thesis; it needs a cost next to it. eBOPs run on the laptop. Latency and resources come from csynth on mulder. Copy every report home as soon as it lands.

  9. Write it down, question first

    One experiment-log entry per campaign in the Question / Design / Result / Interpretation / Ops shape. Record failed approaches too, with the reason, so nobody tries them again.

  10. Hand Claude the judgment work, not the typing

    Do it yourself

    Launch, check, read logs, delete, the lab pod, ssh to mulder, reading W&B curves, deciding what enters the record.

    Hand to Claude

    Changing generators or training code, recomputing numbers into VERIFY.md, review and red-team before anything goes out, diagnosing a crash from a pasted log in a fresh session.

Non-negotiables

Rules of the road

Every number carries four labels

Metric (validation vs ROC-test AUC), split, n, status (single seed vs seed-averaged). Recomputed from .npz or csynth JSON, never from memory or W&B alone.

No gap without an interval

At least 3 seeds. Inside the seed spread is flat.

Compare like with like

Same N, same input set. Cross-N comparisons only when that is the question.

Binary is the thesis

{−1,+1} weights. Ternary and FP32 are baselines.

Scratch is never quotable

Anything from the lab pod or the laptop kernel stays out of the record.

Code is frozen during a run

A fix is a new preflight and a new md5, never a patch to a live round.

Words

Glossary

N, n_part
number of jet constituents fed to the transformer (8, 16, 32, 64). Attention cost grows as N².
l1x3
the L1-realistic 3-feature input set used from round 14. Results only compare within it.
w1a8, w1a4 …
weight bits / activation bits. w1 = binary {−1,+1} weights, the thesis.
fp32, w8a8
full-precision and 8-bit baselines.
validation AUC
the training monitor. Never published.
ROC-test AUC
macro one-vs-rest AUC over 5 classes on the held-out split, n = 260,000. The published number.
eBOPs
effective bit operations, a hardware cost proxy. HGQ2-native convention only.
HGQ2, hls4ml
quantization-aware training library; the converter from a trained model to HLS code.
csynth
Vitis HLS C synthesis: latency, LUT, FF, DSP, BRAM estimates. Target VU13P at 2.5 ns.
Job / Indexed Job / pod
the order; an order with many numbered runs; the disposable worker.
ConfigMap
the frozen code tarball the pods unpack. Under 1 MB.
PVC
persistent cluster disk. The current pipeline doesn't use one; the lab notebook pod does.
campaign
one study folder carrying its five phase files.
JFC
the agent framework from Moreno et al. (arXiv:2603.20179) this repo's process is adapted from.
PASS / ITERATE / ESCALATE
review verdicts: advance; fix and re-review; needs you.

Known gaps in this copy of the repo

No git

Nothing under ~/lab/bnjettag is a git repository, so "commit each change" and code shas in PREFLIGHT can't happen yet. The ConfigMap md5 is the only proof of which code ran.

Agents and slash commands are missing

.claude/agents/ and .claude/commands/ don't exist here, so /review, /new-experiment and the reviewer panel described in SYSTEM.md won't run in this folder.

ROC ConfigMap has no build script

kai-bn14-roc-code is mounted by the eval jobs but nothing here builds it (runbook, Phase 6).

Paths in older docs

Some runbooks still say ~/Downloads/bnjettag-training-results or ~/Desktop/bnjettag. On this machine it's ~/lab/bnjettag.
