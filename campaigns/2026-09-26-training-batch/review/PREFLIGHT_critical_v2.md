### Ruling on flagged decision 6 (CPU certification vs the training GPU class)

**Accepted, with four conditions. It governs readout interpretation and the production gate, not the pilot launch.**
- A CPU `CERTIFIED` is sufficient. A reset retrace on the full split that reproduces a GPU-logged value within rel 1e-6 does not happen by coincidence: one moved integer bit shifts EBOPs by thousands.
- A CPU `EBOPS_MISMATCH` is ambiguous, because the docstring of `certify_ebops.py` names the power-of-two rounding path.

The four conditions:
1. **Pre-register it.** Date the rule in decisions.md (or as a STUDY amendment beside l. 1275-1277) *before the readout Job is applied*, not after a mismatch appears. It allows one GPU re-run: the same files and the same bundle, TF32 off, pinned by `nvidia.com/gpu.product` to the product RUN.md records for the pilot. The GPU result is final, with no third run.
2. **Gate on the stored sum first.** `certify_checkpoint` labels `EBOPS_MISMATCH` before `STORED_MISMATCH` (`certify_ebops.py:89-90`), so a device-independent stored mismatch can hide behind the EBOPS label. The re-run rule applies only to records where `stored_ebops == logged_ebops`. Where they differ, the file is a defect whatever the device.
3. **Name the GPU readout manifest path.** No GPU readout manifest exists. Name the `freeze.py` output (for example a `readout-gpu-job.json` with the product pinned and `requirements-training.txt`). Because `certify_ebops.py` and `analysis/` sit outside `manifest()`, this needs at most a new manifest, and never a change to a run's `code_sha256`.
4. **Report any CPU/GPU disagreement.** Such a disagreement is a finding for production's terminal certification, which should then run on the training GPU class as the docstring says. It is never silently absorbed.
