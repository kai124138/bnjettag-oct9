Run: python3 publication/code/launch/test_batch_launch.py.

One meaningful manifest issue was found and fixed by the root agent before GPU launch: podReplacementPolicy now equals Failed. Kubernetes documents that its default replacement policy can temporarily exceed parallelism while Pods terminate; waiting for terminal failure avoids that normal replacement overlap. [Official Job documentation](https://kubernetes.io/docs/concepts/workloads/controllers/job/).

Checkpoint writes already have a nonblocking per-run flock in run_ablation.py. The new wrapper delegates training to that existing entrypoint. Thus rare duplicate Indexed Pods cannot train the same run concurrently. The wrapper's status marker itself lies outside that lock and can be transiently overwritten by a duplicate failing attempt; treat committed checkpoint state and W&B progress as authoritative. A bad cache check exits before child training. Such failures leave the wrapper's local cache-lock handle for process-exit cleanup, producing harmless ResourceWarnings in the in-process negative tests; this does not retain the lock after the actual Pod process exits.

Cache checks cover N, feature names, shapes, feature and label hashes, finiteness, label row sums, split seed and order seed. Immutable preflight caches plus distinct n8/n16/n32 roots are essential: the wrapper releases its shared cache lock before the child reloads arrays. The reviewed launch flow prepares these caches first and does not rewrite committed data during training. Compute agent confirmed requirements-training.txt is staged at the archive root expected by the GPU command; it is intentionally absent from the source hgq2 directory itself.

Anonymous W&B status retrieval

The documented wandb.Api wrapper requires an API key (and may prompt if absent); the name Public API does not promise anonymous SDK initialization. [Official Api reference](https://docs.wandb.ai/models/ref/python/public-api/api).

However, an explicit anonymous read-only POST to the official https://api.wandb.ai/graphql endpoint empirically returned public run state and summaryMetrics from the documented public wandb/jobs example. No credentials were loaded or transmitted. A second public example also returned run state. Evidence and the exact query are in anonymous-wandb-read-check.json. The user's new project returned project:null before its first GPU run; that response cannot distinguish a nonexistent project from a private one.

Once the project exists and is publicly readable, a scheduled GitHub Action can make this read query with runs(first:100), paginate if necessary, and publish only allowlisted summary fields. Important fields are completed_epochs, screening_target_epochs, phase, best_feasible_val_accuracy, best_feasible_val_macro_auc, best_feasible_ebops, and both documented epoch-number conventions. Use the fixed 12-run planning manifest to show not-yet-observed runs without misclassifying them as failed. A W&B finished run with phase=paused_for_promotion has finished its screening rung, not the immutable 1,000-epoch experiment.

Use the GitHub Action's repository-scoped built-in token for committing the snapshot; no GitHub credentials need to be placed on the cluster. Preserve the last valid snapshot and annotate fetch failure/staleness if the API is unavailable or project:null. Direct GraphQL schema access should have a small compatibility test because the documented Python client is the supported abstraction. If public reads are unavailable, use a W&B credential stored only in GitHub Actions, limited to the project's required access, and the documented api.runs(path) export method. Never print that credential or embed it in generated HTML/JSON. [Official export guide](https://docs.wandb.ai/models/track/public-api-guide).

No external writes or frozen training-code edits were performed for this review.
